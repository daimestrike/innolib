# Библиотека инноваций

Реестр инновационных проектов и идей с ИИ-консультантом:
- воронка стадий, поиск и фильтры, выгрузка в Excel;
- мастер из 4 вопросов с разбором ответов через LLM и подсказкой похожих проектов;
- **консультант** — чат, который отвечает по реестру и базе знаний (RAG): что уже делали, на что похожа идея, как её проверить; ссылается на кейсы кодами `[INN-012]` и на документы `[DOC-3]`;
- **генератор идей** — по описанию проблемы предлагает несколько идей с опорой на существующие кейсы, с эффектом и способом проверки; идею можно сразу отправить в реестр или обсудить с консультантом;
- идею из диалога можно одной кнопкой оформить в карточку реестра.

**Работает в закрытом контуре без интернета.**
- Сервер использует только стандартную библиотеку Python 3.9+, `pip install` не нужен.
- База — один файл SQLite.
- Шрифты лежат в `static/fonts`, внешних CDN нет.
- LLM необязателен. Без него мастер работает, а консультант показывает найденные кейсы без ответа модели.

## Документация

Подробное описание проекта лежит в папке [`wiki/`](wiki/README.md): что это и зачем, руководство пользователя, устройство системы, развёртывание, наполнение реестра, API, частые вопросы и планы развития. Каждый документ можно перенести в корпоративную вики отдельной страницей.

## Скачать

Готовые архивы лежат в [Releases](https://github.com/daimestrike/innolib/releases):
- `innolib-<версия>.tar.gz` — исходники, запуск через `python3 app.py` или сборка образа в контуре;
- `innolib-image-<версия>.tar.gz` — готовый Docker-образ (`docker load -i …`);
- `SHA256SUMS.txt` — контрольные суммы для проверки после переноса.

Текущая версия — в файле `VERSION`. Её также показывают `/healthz`, `/api/config` и подвал интерфейса.

## Состав

```
app.py                  сервер + CLI (import, export, add-doc, check-llm, reindex)
llm.py                  клиент OpenAI-совместимого API (обычный и потоковый ответ, эмбеддинги)
rag.py                  поиск для консультанта: BM25 по-русски + опционально эмбеддинги
docs.py                 извлечение текста из TXT, MD, HTML, DOCX
static/                 интерфейс: index.html, app.js, app.css, шрифты
data/seed_demo.json     16 демо-кейсов (грузятся в пустую базу, если SEED_DEMO=1)
data/import_template.csv  шаблон для загрузки реальных проектов
Dockerfile, docker-compose.yml, .env.example
deploy/innolib.service  запуск через systemd без Docker
deploy/nginx.conf.example  публикация под префиксом /innolib/
build_offline.sh        сборка архива и Docker-образа для переноса в контур
```

## Быстрый старт

```bash
python3 app.py
# открыть http://<сервер>:8080
```

## Развёртывание в контуре

### Вариант 1. Docker, готовый образ из релиза

Скачать из Releases оба архива и перенести в контур:
```bash
sha256sum -c SHA256SUMS.txt
docker load -i innolib-image-1.2.1.tar.gz
tar xzf innolib-1.2.1.tar.gz && cd innolib-1.2.1
cp .env.example .env          # заполнить: адрес, модель и ключ API
INNOLIB_VERSION=1.2.1 docker compose up -d   # образ уже загружен, сборка не нужна
docker compose exec innolib python3 app.py check-llm   # проверить подключение к модели
```
Собрать то же самое локально: `./build_offline.sh` кладёт архивы в `dist/`.

### Вариант 2. Docker, сборка внутри контура

Нужен только базовый образ Python из внутреннего реестра:
```bash
docker build --build-arg BASE_IMAGE=<внутренний-реестр>/python:3.12-slim --build-arg VERSION=$(cat VERSION) -t innolib:latest .
docker compose up -d
```

### Вариант 3. Без Docker (systemd)

Достаточно `python3` на сервере. Команды описаны в шапке `deploy/innolib.service`.

База хранится в томе `innolib-data` (Docker) или в `data/innolib.sqlite3` (systemd). Резервная копия — это просто копия файла, либо `GET /api/export.json`.

## Настройки (.env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | 8080 | порт |
| `DB_PATH` | data/innolib.sqlite3 | файл базы |
| `SEED_DEMO` | 1 | загрузить демо-кейсы в пустую базу |
| `ADMIN_TOKEN` | пусто | включает удаление кейсов и документов через API (заголовок `X-Admin-Token`) |
| `LLM_URL` | пусто | OpenAI-совместимый endpoint до `/v1` включительно |
| `LLM_MODEL` | пусто | модель для разбора карточек и чата |
| `LLM_CHAT_MODEL` | = `LLM_MODEL` | отдельная модель для консультанта |
| `LLM_API_KEY` | пусто | ключ (заголовок `Authorization: Bearer …`) |
| `LLM_TIMEOUT` | 90 | таймаут запроса к модели, сек |
| `LLM_EXTRA_JSON` | пусто | доп. параметры запроса, например `{"chat_template_kwargs":{"enable_thinking":false}}` |
| `LLM_CA_BUNDLE` / `LLM_VERIFY_TLS` | — / 1 | внутренний сертификат для HTTPS |
| `LLM_USE_SYSTEM_PROXY` | 0 | 1 — ходить к API через `HTTPS_PROXY` |
| `RAG_TOP_K` | 6 | сколько найденных фрагментов подставлять в контекст |
| `EMBED_MODEL` / `EMBED_URL` | пусто | модель эмбеддингов для гибридного поиска (необязательно) |

Файл `.env` рядом с `app.py` подхватывается автоматически, в том числе без Docker. **Ключ API храните только в `.env` на сервере — в git он не попадает.**

Модель подключается к любому серверу с API `/v1/chat/completions`: vLLM, Ollama, LiteLLM, TGI и корпоративные шлюзы. Если шлюз использует свой протокол, поставьте перед ним LiteLLM-прокси. Блоки рассуждений `<think>…</think>` у reasoning-моделей вырезаются автоматически.

Проверка подключения:
```bash
python3 app.py check-llm
```
Команда покажет, видна ли модель в `/models`, и сделает пробный обычный и потоковый запрос.

## Консультант и база знаний (RAG)

Как отвечает консультант:
1. По последним сообщениям пользователя ищутся самые подходящие кейсы и фрагменты документов (BM25 со стеммингом для русского и расшифровкой сокращений: CV, OCR, КСО, ИИ…).
2. В контекст модели попадают: сводка реестра (сколько кейсов по стадиям и направлениям), каталог всех кейсов (код, название, стадия) и подробный текст найденных фрагментов.
3. Модель отвечает потоком, ссылаясь на кейсы и документы кодами. Под ответом видны источники, по клику открывается карточка или фрагмент документа.

База знаний — это стратегии, регламенты, выгрузки страниц вики. Документы добавляются кнопкой «Добавить документ» на вкладке «Консультант» или из командной строки:
```bash
python3 app.py add-doc стратегия.docx регламент.md
```
Поддерживаются TXT, MD, CSV, HTML и DOCX. PDF нужно сохранить как DOCX.

Если на шлюзе есть модель эмбеддингов, задайте `EMBED_MODEL`, и поиск станет гибридным (ключевые слова + смысловая близость). Векторы считаются в фоне и кэшируются в базе; пересчитать их вручную можно командой `python3 app.py reindex`. Без эмбеддингов BM25 хорошо справляется на реестре из сотен кейсов.

### Генератор идей

Вкладка «Генератор идей»: описываете проблему или область (есть готовые темы), выбираете направление и количество. Модель получает тот же контекст, что и консультант (сводка, каталог, найденные кейсы и документы), и возвращает карточки идей:
- суть решения и проблема;
- ожидаемый эффект;
- как проверить за 2–4 недели;
- что нового по сравнению с реестром;
- на какие кейсы опирается. Коды сверяются с реестром, выдуманные отбрасываются.

«Ещё идеи» просит новые, не повторяя уже предложенные. «В реестр» открывает мастер с заполненной карточкой, «Обсудить с консультантом» переносит идею в чат.

История чата хранится в браузере пользователя, на сервер уходят только сообщения текущего диалога.

## Загрузка реальных проектов

1. Заполните `data/import_template.csv` в Excel и сохраните как CSV UTF-8. Разделитель `;` или `,`.
   - Стадии можно писать по-русски: идея, проработка, пилот, внедрено, остановлено.
   - Тип: проект или идея. Эффект: план или факт. Теги перечисляются через `;`.
2. Загрузите файл:
```bash
python3 app.py import cases.csv
# в Docker:
docker compose exec innolib python3 app.py import /data/cases.csv
```
Для Docker файл нужно сначала положить в том `/data`, например через `docker cp`.

Чтобы не загружать демо-кейсы: задайте `SEED_DEMO=0` до первого запуска, либо удалите базу и запустите заново.

## API

| Метод | Путь | |
|---|---|---|
| GET | `/api/cases` | все кейсы |
| POST | `/api/cases` | создать (код INN-xxx назначается сервером) |
| PATCH | `/api/cases/<id>` | изменить поля |
| DELETE | `/api/cases/<id>` | удалить (нужен `ADMIN_TOKEN`) |
| POST | `/api/parse` | разбор ответов мастера через LLM |
| POST | `/api/chat` | консультант, ответ потоком SSE: `sources`, `delta`, `done`, `error` |
| POST | `/api/ideas` | генерация идей: `{topic, direction?, count?, exclude?}` → `{ideas:[…]}` |
| GET | `/api/search?q=` | поиск по реестру и базе знаний (для отладки RAG) |
| GET, POST | `/api/docs` | список и добавление документов (`{filename, contentBase64}` или `{title, text}`) |
| DELETE | `/api/docs/<id>` | удалить документ (нужен `ADMIN_TOKEN`) |
| GET | `/api/export.csv`, `/api/export.json` | выгрузка |
| GET | `/healthz` | проверка живости |

## Выпуск новой версии

1. Поднять номер в `VERSION` по SemVer: исправление → PATCH, новая функция → MINOR, несовместимое изменение → MAJOR.
2. Добавить раздел в `CHANGELOG.md`.
3. Закоммитить и запушить в `main`.

GitHub Actions увидит новую версию в `VERSION`, поставит тег `vX.Y.Z`, соберёт архив и Docker-образ и опубликует релиз с заметками из CHANGELOG. Запустить выпуск вручную можно так: Actions → Release → Run workflow.

## Обновление в контуре

База хранится отдельно от кода (том `innolib-data` или `data/`), поэтому обновление не трогает кейсы:
```bash
docker load -i innolib-image-<новая>.tar.gz
INNOLIB_VERSION=<новая> docker compose up -d
```
Перед обновлением стоит сохранить резервную копию: `GET /api/export.json`.

## Ограничения прототипа

- Нет авторизации: доступ ограничивается сетью или reverse-proxy с SSO.
- Вики не читается автоматически. Текст страницы вставляется в мастер вручную. Интеграцию с API вики (Confluence и т.п.) можно добавить в `app.py`.
- Похожие проекты в мастере считаются по ключевым словам в браузере.
- Консультант не видит вложения и картинки, только текст кейсов и документов.
