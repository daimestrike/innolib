# Развёртывание и эксплуатация

Документ для администраторов. Здесь всё, что нужно, чтобы поднять систему в закрытом контуре, подключить модель, обновлять версии и разбираться с проблемами.

## Что нужно от сервера

- Linux-сервер или виртуальная машина. Хватит 1 vCPU и 1 ГБ памяти: сервер лёгкий, вся тяжёлая работа на стороне LLM-шлюза.
- **Одно из двух:** Docker с Compose **или** Python 3.9 и новее.
- Сетевой доступ с сервера к корпоративному LLM-шлюзу по HTTPS.
- Около 100 МБ на диске под приложение плюс место под базу. База растёт медленно: тысяча кейсов с документами — это единицы мегабайт.

Доступ в интернет не нужен. Ни при установке, ни при работе система никуда наружу не обращается.

## Где взять дистрибутив

Все версии публикуются в разделе [Releases](https://github.com/daimestrike/innolib/releases) репозитория. В каждом релизе три файла:

| Файл | Что это |
|---|---|
| `innolib-<версия>.tar.gz` | Исходники: код, интерфейс, шрифты, конфиги, документация |
| `innolib-image-<версия>.tar.gz` | Готовый Docker-образ, собранный из этих исходников |
| `SHA256SUMS.txt` | Контрольные суммы, чтобы проверить файлы после переноса в контур |

Скачайте файлы на машине с интернетом и перенесите в контур принятым у вас способом. После переноса проверьте целостность:

```bash
sha256sum -c SHA256SUMS.txt
```

## Вариант 1. Docker с готовым образом (рекомендуем)

Самый простой путь: ничего не собирается внутри контура.

```bash
# 1. Загрузить образ
docker load -i innolib-image-1.2.1.tar.gz

# 2. Распаковать исходники (нужны docker-compose.yml и пример настроек)
tar xzf innolib-1.2.1.tar.gz
cd innolib-1.2.1

# 3. Настройки
cp .env.example .env
nano .env          # адрес шлюза, модель, ключ (см. раздел «Настройки»)

# 4. Запуск
INNOLIB_VERSION=1.2.1 docker compose up -d

# 5. Проверка
curl http://localhost:8080/healthz
docker compose exec innolib python3 app.py check-llm
```

Данные хранятся в Docker-томе `innolib-data` и переживают перезапуск и обновление контейнера.

## Вариант 2. Docker со сборкой внутри контура

Если готовый образ перенести нельзя, но во внутреннем реестре есть базовый образ Python:

```bash
tar xzf innolib-1.2.1.tar.gz && cd innolib-1.2.1
docker build \
  --build-arg BASE_IMAGE=<внутренний-реестр>/python:3.12-slim \
  --build-arg VERSION=$(cat VERSION) \
  -t innolib:1.2.1 .
cp .env.example .env && nano .env
INNOLIB_VERSION=1.2.1 docker compose up -d
```

При сборке ничего не скачивается: `pip install` в Dockerfile нет.

## Вариант 3. Без Docker, через systemd

Подходит, если на сервере есть только Python.

```bash
sudo useradd --system --home /opt/innolib innolib
sudo mkdir -p /opt/innolib
sudo tar xzf innolib-1.2.1.tar.gz -C /opt/innolib --strip-components=1
sudo cp /opt/innolib/.env.example /opt/innolib/.env
sudo nano /opt/innolib/.env
sudo chown -R innolib /opt/innolib
sudo chmod 600 /opt/innolib/.env

sudo cp /opt/innolib/deploy/innolib.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now innolib

sudo -u innolib python3 /opt/innolib/app.py check-llm
```

База будет лежать в `/opt/innolib/data/innolib.sqlite3`. Логи смотрятся через `journalctl -u innolib -f`.

Для быстрой проверки можно запустить и совсем без установки: `python3 app.py` в распакованной папке. Файл `.env` рядом с `app.py` подхватывается автоматически.

## Настройки

Все настройки задаются в файле `.env`. Переменные окружения, заданные явно, важнее значений из файла.

### Основные

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `PORT` | `8080` | Порт веб-сервера |
| `DB_PATH` | `data/innolib.sqlite3` | Путь к файлу базы. В Docker задан как `/data/innolib.sqlite3` |
| `SEED_DEMO` | `1` | Загрузить 16 демо-кейсов, если база пустая. Для боевого запуска ставьте `0` |
| `ADMIN_TOKEN` | пусто | Секрет для удаления кейсов и документов через API. Пусто — удаление выключено |

### Модель

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `LLM_URL` | пусто | Адрес OpenAI-совместимого API **до `/v1` включительно**, например `https://llm-gateway.company.local/v1` |
| `LLM_MODEL` | пусто | Идентификатор модели так, как его знает шлюз |
| `LLM_API_KEY` | пусто | Ключ API. Уходит в заголовке `Authorization: Bearer …` |
| `LLM_CHAT_MODEL` | как `LLM_MODEL` | Отдельная модель для консультанта и генератора, если хочется использовать для чата более сильную |
| `LLM_TIMEOUT` | `90` | Сколько секунд ждать ответа модели |
| `LLM_EXTRA_JSON` | пусто | Дополнительные параметры запроса в JSON. Например, `{"chat_template_kwargs":{"enable_thinking":false}}` отключает рассуждения у моделей семейства Qwen3 и ускоряет ответ |
| `LLM_CA_BUNDLE` | пусто | Путь к корневому сертификату, если шлюз использует внутренний CA |
| `LLM_VERIFY_TLS` | `1` | `0` отключает проверку сертификата. Только для диагностики |
| `LLM_USE_SYSTEM_PROXY` | `0` | `1` — ходить к шлюзу через `HTTPS_PROXY`. По умолчанию напрямую |

**Какую модель выбрать.** Для старта хватит самой лёгкой модели шлюза: разбор карточек и ответы по реестру не требуют больших рассуждений, а лёгкая модель отвечает быстрее. Если ответы консультанта покажутся поверхностными, задайте `LLM_CHAT_MODEL` с моделью покрупнее, а разбор карточек оставьте на лёгкой.

### Поиск

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `RAG_TOP_K` | `6` | Сколько найденных фрагментов подставлять в контекст консультанта |
| `EMBED_MODEL` | пусто | Модель эмбеддингов. Если задана, поиск становится гибридным |
| `EMBED_URL` | как `LLM_URL` | Адрес API эмбеддингов, если он отличается |

### Ключ API

Ключ — персональное средство доступа, относитесь к нему как к паролю:
- храните его только в `.env` на сервере и ограничьте права на файл (`chmod 600`);
- не коммитьте `.env` в git (он уже в `.gitignore`);
- для промышленной эксплуатации лучше получить сервисный ключ, а не использовать личный;
- если ключ мог утечь (попал в чат, на скриншот, в тикет), перевыпустите его на портале шлюза и обновите `.env`.

## Проверка подключения к модели

```bash
python3 app.py check-llm
# в Docker:
docker compose exec innolib python3 app.py check-llm
```

Команда по шагам проверяет:
1. доступен ли список моделей `/models` и есть ли в нём указанная модель;
2. работает ли обычный запрос (печатает ответ и время);
3. работает ли потоковый запрос, на котором построен чат;
4. если задан `EMBED_MODEL`, работают ли эмбеддинги.

При успехе команда завершается с кодом 0, её можно использовать в скриптах мониторинга.

## Публикация через nginx

Обычно приложение ставят за reverse-proxy: он даёт HTTPS, корпоративный SSO и красивый адрес. Пример лежит в `deploy/nginx.conf.example`:

```nginx
location /innolib/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 180s;     # запас на длинный ответ модели
    proxy_buffering off;         # консультант отвечает потоком
    client_max_body_size 25m;    # загрузка документов
}
```

Три строки здесь важны:
- `proxy_buffering off` — без неё ответ консультанта будет приходить не по словам, а целиком в конце;
- `proxy_read_timeout` — должен быть больше `LLM_TIMEOUT`;
- `client_max_body_size` — иначе nginx не пропустит загрузку документов больше 1 МБ.

Приложение само понимает, что работает под префиксом (`/innolib/`), отдельно настраивать его не нужно.

## Первый запуск с реальными данными

1. В `.env` поставьте `SEED_DEMO=0`, чтобы не загружать демо-кейсы.
2. Запустите приложение.
3. Загрузите реестр из Excel (подробности в [Данные и наполнение](05-dannye-i-napolnenie.md)):
   ```bash
   python3 app.py import cases.csv
   ```
4. Загрузите ключевые документы в базу знаний:
   ```bash
   python3 app.py add-doc стратегия.docx регламент_пилотов.docx
   ```
5. Откройте систему в браузере и задайте консультанту пару вопросов для проверки.

Если демо-кейсы уже загрузились, а нужен чистый реестр, остановите приложение, удалите файл базы (или Docker-том `innolib-data`) и запустите заново с `SEED_DEMO=0`.

## Обновление версии

База хранится отдельно от кода, поэтому обновление не трогает данные. Перед обновлением всё равно сделайте резервную копию.

**Docker:**
```bash
docker load -i innolib-image-<новая>.tar.gz
INNOLIB_VERSION=<новая> docker compose up -d
```

**systemd:**
```bash
sudo systemctl stop innolib
sudo tar xzf innolib-<новая>.tar.gz -C /opt/innolib --strip-components=1   # .env и data/ не перезаписываются
sudo chown -R innolib /opt/innolib
sudo systemctl start innolib
```

Что изменилось в каждой версии, смотрите в `CHANGELOG.md`. Версия, которая сейчас работает, видна в подвале интерфейса и в ответе `/healthz`.

## Резервное копирование

Есть два способа, лучше использовать оба.

**Копия файла базы.** Это полная копия, включая документы базы знаний.
```bash
# systemd
# корректная копия «на ходу», без остановки сервиса; нужен только python3
python3 -c "import sqlite3,sys; sqlite3.connect(sys.argv[1]).backup(sqlite3.connect(sys.argv[2]))" \
  /opt/innolib/data/innolib.sqlite3 /backup/innolib-$(date +%F).sqlite3
# Docker
docker run --rm -v innolib-data:/data -v /backup:/backup alpine \
  cp /data/innolib.sqlite3 /backup/innolib-$(date +%F).sqlite3
```

**Выгрузка реестра в JSON.** Она читается человеком, и её можно загрузить обратно командой `import`. Документы базы знаний в неё не входят.
```bash
curl -o innolib-$(date +%F).json http://localhost:8080/api/export.json
```

Разумный минимум — ежедневная копия файла базы с хранением за 30 дней.

## Мониторинг

- `GET /healthz` отвечает `{"ok": true, "version": "…", "cases": N}`. Его удобно подключить к системе мониторинга. В Docker-образ уже встроен healthcheck.
- Логи пишутся в stderr: в Docker — `docker compose logs -f`, в systemd — `journalctl -u innolib -f`. По каждому запросу к модели пишется время ответа и число источников, например `chat ok: 1840 симв. за 6.2s, источников 6`.
- `python3 app.py check-llm` — периодическая проверка связи с моделью.

## Диагностика

| Что видим | Скорее всего | Что делать |
|---|---|---|
| В подвале «модель не подключена» | Не заданы `LLM_URL` или `LLM_MODEL`, или `.env` не подхватился | Проверьте `.env` рядом с `app.py` (или `env_file` в compose) и перезапустите |
| `check-llm`: `CERTIFICATE_VERIFY_FAILED` | Шлюз использует внутренний сертификат | Укажите путь к корневому сертификату в `LLM_CA_BUNDLE`. Для Docker файл нужно смонтировать в контейнер |
| `check-llm`: `HTTP 401` / `403` | Неверный или просроченный ключ | Перевыпустите ключ и обновите `LLM_API_KEY` |
| `check-llm`: `HTTP 404` | Неверный адрес: чаще всего забыт `/v1` на конце | `LLM_URL` должен заканчиваться на `/v1` |
| `check-llm`: модель «НЕ НАЙДЕНА в списке» | Опечатка в идентификаторе | Скопируйте id модели из вывода `/models` |
| `check-llm`: «LLM недоступен: timed out» / «Name or service not known» | Сервер не видит шлюз по сети | Проверьте DNS и маршрут. Если в контуре нужен прокси, поставьте `LLM_USE_SYSTEM_PROXY=1` и задайте `HTTPS_PROXY` |
| Ответ консультанта появляется целиком в конце, а не по словам | Буферизация на reverse-proxy | `proxy_buffering off` в nginx |
| Консультант отвечает очень долго | Модель долго «думает» | Попробуйте `LLM_EXTRA_JSON={"chat_template_kwargs":{"enable_thinking":false}}` или более лёгкую модель |
| Генератор: «Модель вернула идеи не в формате JSON» | Лёгкая модель иногда ломает формат | Просто повторите запрос. Если повторяется часто, задайте `LLM_CHAT_MODEL` с моделью покрупнее |
| Не загружается документ: 413 | Ограничение размера на прокси | Увеличьте `client_max_body_size` |
| «Удаление доступно только администратору» | Не задан `ADMIN_TOKEN` или не передан заголовок | Задайте токен и передавайте `X-Admin-Token` |
